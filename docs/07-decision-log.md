# Decision Log

Status: **Active**, **Amended** (still in force but changed — see the note), or **Superseded** (replaced by a later decision).

| ID      | Decision                                                            | Rationale                                                                                                                                                           | Date     | Alternatives Considered                            | Status |
| ------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------- | ------ |
| DEC-001 | Use Firebase Firestore over a custom REST API                       | Real-time updates via `onSnapshot` without WebSocket infrastructure. Reduces backend complexity for a single-admin app.                                             | Mar 2026 | Supabase, custom Express API                       | Active |
| DEC-002 | Inactive flag instead of delete for stylists/services               | Preserves referential integrity on historical bookings. Deactivated stylist's past bookings remain queryable and display correctly.                                 | Mar 2026 | Hard delete, soft delete with deleted_at timestamp | Active |
| DEC-003 | Tiered pricing stored as object on service, not separate collection | Simpler reads — one document fetch gets all tiers. Price resolved at booking time and stored flat on the booking.                                                   | Mar 2026 | Separate pricing collection, junction table        | Active |
| DEC-004 | Price history as append-only array on service document              | Full audit trail without a separate collection. `arrayUnion` ensures atomicity. Historical bookings reconcilable against price active on their date.                | Mar 2026 | Separate price_history collection                  | Active |
| DEC-005 | All business rules in `config.ts`                                   | Single source of truth. Owner can request rule changes (notice period, cutoff, slot interval) without touching scheduling logic. **Amended by DEC-020:** opening hours and closed days are now owner-editable data in Firestore; `config.ts` keeps them only as the fallback default. | Mar 2026 | Hardcoded in scheduling functions                  | Amended |
| DEC-006 | Scheduling engine in minutes from midnight                          | Avoids AM/PM string parsing bugs in time comparisons. All slot logic operates on integers.                                                                          | Mar 2026 | String comparison, Date objects                    | Active |
| DEC-007 | Allow bookings during rest periods if new service fits              | Directly modelled from how Steve manages his floor — a colour client sitting with product does not block him from starting a men's cut. Significant revenue impact. A booking's **active** time must fit inside the remaining rest window. | Mar 2026 | Block stylist entirely during rest period          | Active |
| DEC-008 | Readable booking IDs: `{date}_{stylist-name}_{timestamp}`           | Human-readable in Firebase console. Easier debugging. No collision risk due to timestamp suffix. **Superseded by DEC-016:** admin-created bookings used a form of this ID *without* the timestamp and silently overwrote each other; all bookings now use auto-generated IDs. | Mar 2026 | Auto-generated Firestore IDs                       | Superseded |
| DEC-009 | `onSnapshot` for bookings, `getDocs` for stylists/services          | Bookings change frequently (real-time needed). Stylists and services change rarely (one-time fetch sufficient, with manual refetch after mutations). **Amended:** the bookings subscription is bounded to a rolling 90-day window (Analytics and client search query on demand); `salonSettings` and notifications are also live. | Mar 2026 | `onSnapshot` for all collections                   | Amended |
| DEC-010 | Optimistic UI updates with rollback                                 | Admin dashboard feels instant. Status changes reflect immediately without waiting for Firestore round-trip. Rollback restores previous state if write fails.        | Mar 2026 | Wait for Firestore confirmation before updating UI | Active |
| DEC-011 | ToastContext over prop drilling for notifications                   | Any component can trigger a toast without threading `addToast` through every page component. Cleaner component interfaces.                                          | Apr 2026 | Prop drilling through page components              | Active |
| DEC-012 | Denormalised stylist name and price on booking document             | Booking record is self-contained for analytics and display. Eliminates join queries. Accurate even after stylist deactivation or price change.                      | Mar 2026 | Join to stylists/services at query time            | Active |
| DEC-013 | Public availability reads a PII-free `slotBlocks` projection, not `bookings`; `bookings` is staff-only | Firestore rules cannot hide individual fields from an authorised read, so any public read of `bookings` would expose names, phones and notes to anyone with the public web config. Every booking write also writes its projection atomically. | Jul 2026 | Field-level rules (not possible); a Cloud Function API | Active |
| DEC-014 | `customerLookups` is staff-read-only; the public form does not greet or pre-fill returning customers | A phone number is not proof of owning it, so a lookup by number must not return a name or visit count to an anonymous visitor. Cost: the "returning customer" greeting in the original design was removed (TC-002 rewritten). | Jul 2026 | Keep the greeting and accept the disclosure; verify by SMS code | Active |
| DEC-015 | Seven-state booking lifecycle; only `cancelled` and `no_show` free the slot; restoring re-checks the slot | Lets the owner track a client through the day (arrived, in service, completed) while keeping the chair blocked until the client is really gone. A restored booking must not double-book a slot someone else took meanwhile. Undo toast for cancel/no-show. | Oct 2026 | Keep three statuses (pending/confirmed/cancelled); delete cancelled bookings | Active |
| DEC-016 | Every booking gets an auto-generated document ID; the readable reference is stored in `bookingRef` | Supersedes DEC-008. A deterministic ID let a second walk-in/break for the same stylist and start time overwrite the first (commit 233da18). The reference stays human-readable without being a key. | Oct 2026 | Keep readable IDs and add a timestamp suffix (collision still possible within a second; hard to enforce on every path) | Active |
| DEC-017 | Admin writes that claim a slot run in a transaction on a per-stylist-per-day lock document (`stylistDayLocks`) | The Firestore client SDK cannot query inside a transaction, so a check-then-write could let two admins both pass. Reading and bumping a lock document in the same transaction makes concurrent writers serialise; the loser re-runs and sees the other booking. Covers walk-in, break, training, restore and reschedule. **Does not cover online customer bookings** (the public rules do not allow anonymous writes to the lock). Needs the `stylistDayLocks` rule deployed. | Oct 2026 | A Cloud Function owning all booking writes (stronger — would also cover customers — but a larger change); accept the race | Active |
| DEC-018 | Online bookings start `pending` and need owner approval; walk-ins, breaks and training are created `confirmed` | The owner controls the day; the public create rule pins `status == 'pending'` so a customer cannot arrive pre-confirmed. A pending booking still holds its slot. Open question: the customer-facing copy says "confirmed" (see 02, open question 1). | Mar 2026 (original design) | Auto-confirm online bookings | Active |
| DEC-019 | Emails sent by Cloud Functions through Resend; the owner's notification address lives in `privateSettings` | Confirmation (on create), 24-hour reminder (hourly scheduler) and optional owner notification. The address is kept out of the world-readable `salonSettings`. Functions need a Resend key and a verified domain; **not deployed or exercised end to end yet**. | Oct 2026 | Client-side email (exposes keys); SMS | Active (undeployed) |
| DEC-020 | Opening hours and closed days are data in Firestore (`salonSettings/main`): weekly schedule plus per-date overrides, plus per-stylist working hours | The owner can close a date or open a Monday without a developer. `config.ts` remains the fallback. The admin timeline and the public calendar both read the same effective hours. | Jun 2026 | Hours only in `config.ts` | Active |
| DEC-021 | Firestore offline cache uses `persistentLocalCache` (multi-tab) | Replaces the deprecated `enableIndexedDbPersistence`. | May 2026 | No persistence | Active |
| DEC-022 | Browser scenarios run in Playwright against the Firebase emulators, never a real project | Lets the written test scenarios be replayed automatically and safely. The dev server is started with `VITE_USE_EMULATORS=true` and a `demo-` project id, so the real `.env` is never used. | Oct 2026 | Manual testing only; testing against production | Active |
| DEC-023 | Opening, reading or refreshing a protected admin URL waits for the signed-in user's role before redirecting | `/admin/analytics` used to bounce the owner to Today while the role loaded (D7). | Oct 2026 | — | Active |

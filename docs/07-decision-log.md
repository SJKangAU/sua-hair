| DEC-010 | Optimistic UI updates with rollback                                 | Admin dashboard feels instant. Status changes reflect immediately without waiting for Firestore round-trip. | DEC-011 | ToastContext over prop drilling for notifications                   | Any component can trigger a toast without threading `addToast` through every page component. | DEC-012 | Denormalised stylist name and price on booking document             | Booking record is self-contained for analytics and display. Eliminates join queries. Accurate even after stylist deactivation or price change.                      | Mar 2026 | Join to stylists/services at query time            | Active |
| DEC-013 | Public availability reads a PII-free `slotBlocks` projection, not `bookings`; `bookings` is staff-only | Firestore rules cannot hide individual fields from an authorised read, so any public read of `bookings` would expose names, phones and notes to anyone with the public web config. Every booking write also writes its projection atomically. | Jul 2026 | Field-level rules (not possible); a Cloud Function API | Active |
| DEC-014 | `customerLookups` is staff-read-only; the public form does not greet or pre-fill returning customers | A phone number is not proof of owning it, so a lookup by number must not return a name or visit count to an anonymous visitor. Cost: the "returning customer" greeting in the original design was removed (TC-002 rewritten). | Jul 2026 | Keep the greeting and accept the disclosure; verify by SMS code | Active |
| DEC-015 | Seven-state booking lifecycle; only `cancelled` and `no_show` free the slot; restoring re-checks the slot | Lets the owner track a client through the day (arrived, in service, completed) while keeping the chair blocked until the client is really gone. A restored booking must not double-book a slot someone else took meanwhile. Undo toast for cancel/no-show. | Oct 2026 | Keep three statuses (pending/confirmed/cancelled); delete cancelled bookings | Active |
| DEC-016 | Every booking gets an auto-generated document ID; the readable reference is stored in `bookingRef` | Supersedes DEC-008. A deterministic ID let a second walk-in/break for the same stylist and start time overwrite the first (commit 233da18). The reference stays human-readable without being a key. | Oct 2026 | Keep readable IDs and add a timestamp suffix (collision still possible within a second; hard to enforce on every path) | Active |
| DEC-017 | Admin writes that claim a slot run in a transaction on a per-stylist-per-day lock document (`stylistDayLocks`) | The Firestore client SDK cannot query inside a transaction, so a check-then-write could let two admins both pass. Reading and bumping a lock document in the same transaction makes concurrent writers serialise; the loser re-runs and sees the other booking. Covers walk-in, break, training, restore and reschedule. **Does not cover online customer bookings** (the public rules do not allow anonymous writes to the lock). Needs the `stylistDayLocks` rule deployed. | Oct 2026 | A Cloud Function owning all booking writes (stronger — would also cover customers — but a larger change); accept the race | Active |
| DEC-018 | Online bookings start `pending` and need owner approval; walk-ins, breaks and training are created `confirmed` | The owner controls the day; the public create rule pins `status == 'pending'` so a customer cannot arrive pre-confirmed. A pending booking still holds its slot. Open question: the customer-facing copy says "confirmed" (see 02, open question 1). | Mar 2026 (original design) | Auto-confirm online bookings | Active |
| DEC-019 | Emails sent by Cloud Functions through Resend; the owner's notification address lives in `privateSettings` | Confirmation (on create), 24-hour reminder (hourly scheduler) and optional owner notification. The address is kept out of the world-readable `salonSettings`. Functions need a Resend key and a verified domain; **not deployed or exercised end to end yet**. | Oct 2026 | Client-side email (exposes keys); SMS | Active (undeployed) |
| DEC-020 | Opening hours and closed days are data in Firestore (`salonSettings/main`): weekly schedule plus per-date overrides, plus per-stylist working hours | The owner can close a date or open a Monday without a developer. `config.ts` remains the fallback. The admin timeline and the public calendar both read the same effective hours. | Jun 2026 | Hours only in `config.ts` | Active |

| DEC-024 | Customers can start a booking every 15 minutes: `slotIntervalMinutes` changed from 30 to 15, and the booking page's hover preview snaps to the same 15 minutes | Decided by the owner on 2026-10-20. The first version of the hover preview kept starts on the 30-minute grid and showed :15 / :45 as display-only; the owner chose to allow quarter-hour starts instead. Only the interval changed: `generateSlots` still decides every start (clash, rest-window overlap, closing time, 2-hour notice, 5 pm cutoff, closed days, stylist hours) and the UI never re-implements a rule. The preview and the bookable starts now share one grid, so the :15 / :45 "not a start" state cannot occur (the code path remains, exercised by tests with a 30-minute interval). **Consequences:** twice as many start times per day; quarter-hour starts can leave 15-minute gaps that no service fits, so the day can fragment; admin walk-ins already allowed 15-minute starts. To go back, set `slotIntervalMinutes` to 30 in `config.ts`. | Oct 2026 | Keep 30-minute starts with a 15-minute display only (built first, then superseded); snap the preview to the nearest 30-minute start | Active (amends the 30-minute grid) |
| DEC-025 | Stylist display order is an `order` number on each stylist, writable only by the owner | Keeps the data model simple (the public page already reads stylists), needs no new collection or index, and falls back cleanly when missing (existing data unchanged). Reordering renumbers the roster in one batch. The rule is scoped to the `order` field only (other staff writes to stylists are unchanged): any non-owner account can still edit a stylist, but cannot add, change or remove `order`. **Rules must be deployed** for this to be enforced in production. | Oct 2026 | A single ordering document (one write per reorder, but a second read on every page and a place for drift); restricting ALL stylist writes to the owner (a wider change, see PILOT_READINESS risk 3) | Active |
| DEC-026 | A booking is an ordered list of phases `{ type: 'active' \| 'rest', minutes }`; `activeTime` / `restTime` / `totalTime` are derived totals | One hands-on block followed by one rest could not describe a service where the stylist returns to the same client for more hands-on time (Digital Perm: 60 active, 30 rest, 30 active). Phases generalise the model without changing existing data: a service or booking with no stored phases derives them from `activeTime` / `restTime` (`phasesFromLegacy`), so there is no migration and behaviour is identical. A test checks 15,625 legacy combinations give the same answers as before. Each booking stores its own resolved phases and the absolute segments, so a later change to a service never moves an existing booking. | Oct 2026 | Add more legacy fields (`activeTime2`...); migrate every document to phases | Active |
| DEC-027 | Only busy (active) segments conflict, plus a protected return point: the end of a trailing rest phase may not fall strictly inside another booking's busy block. The rule is symmetric. The public `slotBlocks` projection stores `busy` segments and `returnAt` only | The stylist is free during a rest gap, so another client may use it; a later hands-on block must stay free so the stylist can return. Protecting the return point keeps today's two-phase services (hands-on then rest) behaving as before: the stylist still cannot be mid-service on another client at the moment they are due back. The rule is order-independent so the same pair of bookings is judged the same whichever was made first. The new rule allows every start the old one allowed; the only difference is that a new booking's own rest gap may run over an existing booking. `busy` and `returnAt` carry no personal data, so public availability still reads only `slotBlocks` (DEC-013). | Oct 2026 | Conflicts on total time as before; conflicts on busy blocks only with no return point (a stylist could be due back mid-service on someone else) | Active |
| DEC-028 | The owner can change every phase of one booking, at creation and afterwards; the booking keeps its own phases and the stored price never changes. A service's default phases are edited in Manage and affect new bookings only. Every change is re-checked in a transaction | The owner knows a particular client needs more processing time. Changes move later phases, show the new end time live, and are refused with the name and time of the clashing booking, offering "move the return to the next free time" (the smallest 15-minute extension of the rest phase that clears it). Minimums: hands-on at least 15 minutes, 15-minute steps, processing may be 0, the booking must end before closing. Shortening processing while another client is booked in the gap is refused by the same check. The check and the write of the booking, its `slotBlocks` document and its history entry share one transaction on `stylistDayLocks/{date}_{stylistId}` (the client SDK cannot query inside a transaction, so the lock document is read and bumped) so two people cannot both take the free time. **Rules must be deployed before the site** (new fields are validated by `hasValidPhases`: at most 8 entries per list). | Oct 2026 | Edit only the legacy hands-on / rest pair; re-price when phases change; check conflicts only in the browser | Active |
| DEC-029 | What changes from DEC-007 | DEC-007 let another client start inside a rest window if their active time fit. That still holds, now per rest phase. Changes: (1) a service can have several rest phases and hands-on time after a rest; (2) a booking's own rest gap may run over an existing booking, where the old engine blocked the booking's whole length; (3) the point where the stylist returns after a trailing rest is protected (DEC-027); (4) the admin timeline draws one hatched band per rest phase ("Back 11:30 AM") and the resize handle on a block is only offered for hands-on-then-rest bookings, the rest being edited per phase in the booking panel. TC-006 was corrected earlier: its data expected a 45-minute Men's Cut to fit a 30-minute rest window, which contradicts the rule; a 20-minute Beard Trim fits, a 45-minute cut does not. | Oct 2026 | Keep DEC-007 unchanged and add phases beside it | Active (amends DEC-007) |
